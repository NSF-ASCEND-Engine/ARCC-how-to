16  Job arrays: the feature that changes how you work

A job array runs the same script hundreds or thousands of times, each with a different index ($SLURM_ARRAY_TASK_ID). One sbatch, one script, N independent tasks that the scheduler spreads across the cluster and backfills into gaps. For parameter sweeps, ensembles, and per-file processing, this is the single biggest productivity unlock on the machine. MedicineBow allows arrays up to 10,000 tasks.

16.1 The problem it solves

You have 500 fire-weather scenarios to run, or 500 input tiles to process. The wrong way is a bash loop that runs them one after another in a single job (serial, slow, and one crash near the end wastes everything). The other wrong way is copy-pasting 500 submit scripts. The right way is one array job: one script, submitted once, that Slurm turns into 500 independent tasks it can run in parallel and backfill wherever there’s room.

16.2 The mechanics

Add --array and use $SLURM_ARRAY_TASK_ID to pick which piece of work this task does:

#!/bin/bash
#SBATCH --account=cowy-firesurro
#SBATCH --job-name=sweep
#SBATCH --array=1-500                 # 500 tasks, indices 1..500
#SBATCH --qos=fast                    # short independent tasks → high-priority QOS
#SBATCH --time=00:30:00               # per task
#SBATCH --cpus-per-task=2
#SBATCH --mem=8G
#SBATCH --output=logs/sweep-%A_%a.out # %A = array job id, %a = task index

module purge
module load gcc/14.2.0 python/3.12.0

# Use the task index to select this task's work:
python run_scenario.py --scenario-id ${SLURM_ARRAY_TASK_ID}

Submit once:

mkdir -p logs
sbatch submit_array.sh        # creates 500 tasks: 12345_1, 12345_2, ... 12345_500

Each task is scheduled independently. Because they’re small and short, they backfill beautifully (Chapter 14) and the whole sweep can finish far faster than the sum of its parts.

16.3 Driving work from the index

The index is just a number; you map it to real work. Common patterns:

Line N of a parameter file:

PARAM=$(sed -n "${SLURM_ARRAY_TASK_ID}p" params.txt)
python run.py $PARAM

The Nth input file:

FILES=(/project/cowy-firesurro/data/tiles/*.tif)
THIS=${FILES[$SLURM_ARRAY_TASK_ID]}      # note: arrays are 0-indexed in bash
python process.py "$THIS"

(If you index files from a bash array, start --array=0; if you use sed -n Np, start --array=1. Off-by-one here is the classic array bug.)

16.4 Throttling: be a good neighbor

Don’t necessarily unleash all 500 at once — cap how many run simultaneously with %:

#SBATCH --array=1-500%20        # at most 20 tasks running at a time

This keeps you from saturating your account’s core cap (and your fair-share, Chapter 14), while still churning through all 500. A modest % limit is often faster overall because you stop competing with yourself and stay backfill-friendly.

16.5 Managing an array

squeue --me                     # shows pending tasks collapsed, e.g. 12345_[6-500]
scancel 12345                   # cancel the whole array
scancel 12345_7                 # cancel just task 7
sacct -j 12345                  # per-task outcomes after the fact

To find which tasks failed (so you can rerun only those):

sacct -j 12345 --format=JobID,State,ExitCode -n | grep -v COMPLETED

then resubmit just those indices: sbatch --array=17,43,88 submit_array.sh.

Arrays vs. one big MPI job

An array is for independent tasks that don’t talk to each other (embarrassingly parallel): sweeps, ensembles, per-file pipelines. If your tasks must communicate — a single domain-decomposed simulation — that’s an MPI job instead (Chapter 20), a different tool for a different shape of problem.

Arrays are also the natural unit for ensembles in fire/atmospheric work: one array task per ensemble member, each writing to its own output, collected afterward. Reach for them early — most “I need to run this many times” problems are secretly array jobs.

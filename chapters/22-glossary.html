23  Glossary

Plain-language definitions of the terms this book uses.

Account (Slurm)
The project that a job is charged to (e.g. cowy-firesurro). Required on every job via --account. Not your username. See Chapter 10.
ARCC
Advanced Research Computing Center — the UW group that runs MedicineBow.
ASCEND / ARID
The NSF Regional Innovation Engine (ASCEND) and its wildfire-resilience program (ARID) that many readers of this book work under. See the preface.
Backfill
Slurm slotting a small, short job into a gap in the schedule without delaying higher-priority jobs. Why short jobs start fast. See Chapter 14.
Batch job
A job submitted as a script with sbatch that runs unattended when scheduled. The normal way to run work. See Chapter 10.
Checkpoint
A periodic save of a job’s state so it can resume instead of restart after a preemption, timeout, or crash. Essential for long jobs. See Section 18.3.
Compute node
A machine where computation actually runs, allocated to you by Slurm. Distinct from a login node. See Chapter 1.
Condo model
The funding model where research groups buy nodes (inv-*) and others borrow them when idle, subject to reclaim/preemption. See Chapter 18.
Core-hour
One CPU core used for one hour — the unit your allocation is measured in. Reserving 8 cores for 1 hour costs 8 core-hours whether or not you use them.
DenyOnLimit
A QOS flag meaning an over-limit request is rejected at submit time, not silently queued. See Chapter 12.
Fair-share
A priority factor reflecting your account’s recent usage relative to its share; heavy recent use temporarily lowers your priority. See Chapter 14.
GRES (Generic RESource)
How you request GPUs: --gres=gpu:1 or --gres=gpu:h100:2. See Section 17.2.
Investor / inv-*
Nodes/partitions owned by a specific group, who get top priority; others can be preempted off them. See Chapter 18.
Job array
One script run many times with a varying index ($SLURM_ARRAY_TASK_ID), for parameter sweeps and ensembles. Max 10,000 tasks. See Chapter 16.
Lmod / module
The system that loads specific software versions into your shell on demand. Hierarchical: many modules are hidden until you load a compiler. Use module spider. See Chapter 7.
Login node
The shared front-end machine (mblog1, mblog2) you land on when you connect. For editing and submitting — not for computing. See Chapter 1.
MedicineBow
UW/ARCC’s current flagship HPC cluster. The subject of this book.
MPI
Message Passing Interface — the standard for a single parallel program spanning many cores or nodes that communicate. Launched with srun. Contrast with job arrays. See Chapter 20.
OnDemand (Open OnDemand)
The web portal at medicinebow.arcc.uwyo.edu — file browser, terminal, and interactive apps. See Chapter 3.
OOM (Out Of Memory)
When a job exceeds its memory reservation and is killed. Fix by raising --mem. See Chapter 19.
Partition
A named pool of nodes with particular hardware (mb, mb-h100, teton, non-investor, …). Chosen with --partition. See Chapter 12.
Preemption
An investor reclaiming a borrowed node, causing your job to be killed and (here) requeued. See Chapter 18.
Priority
The score that orders pending jobs. On MedicineBow it’s dominated by QOS (weight 200). See Chapter 14.
QOS (Quality of Service)
The service tier that sets your max walltime, resource cap, and priority (debug, fast, normal, long, …). See Chapter 12.
Requeue
Putting a killed (preempted/failed) job back in the pending queue to start over. Pair with checkpointing. See Chapter 18.
Scratch (/gscratch, $SCRATCH)
Fast, large, temporary storage purged after 90 days of inactivity. Not backed up. See Chapter 5.
seff
A command showing a finished job’s CPU and memory efficiency — use it to right-size. See Chapter 15.
Slurm
The scheduler that manages all jobs on the cluster. See Chapter 9.
Snapshot
A point-in-time copy of a filesystem, on the same array as the live data. Protects against accidental deletion, not hardware loss. Not a backup. See Chapter 5.
Walltime
Real elapsed clock time a job is allowed (--time). The job is killed at the limit. See Chapter 11.

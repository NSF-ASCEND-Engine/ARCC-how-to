17  Interactive sessions and GPU jobs

For hands-on work, salloc gives you a live shell on a compute node (start it inside tmux so a dropped connection doesn’t kill it). For GPUs, add --gres=gpu:N and pick a GPU partition — develop on cheap A30s (start in minutes), reserve H100s for jobs that truly need them (start in hours). GPU CUDA work needs the deprecated gcc/13.2.0.

17.1 Interactive sessions with salloc

When you need to poke at things by hand — debug a crash, explore a dataset, build and test a model interactively — request an interactive allocation:

salloc --account=cowy-firesurro --qos=interactive \
       --time=02:00:00 --cpus-per-task=4 --mem=16G

salloc requires at least --account and --time. When it grants the allocation you get a shell on a compute node — now you can run heavy things freely, because you’re no longer on the login node. The interactive QOS is tuned for exactly this: it starts in ~10–30 seconds (Chapter 13) with an 8-hour ceiling.

Launch salloc from inside tmux

An interactive session lives in your shell. If your laptop sleeps or WiFi drops, the shell dies and the session ends. Start tmux on the login node first, then salloc inside it (Section 4.6). Now you can detach, close the laptop, and reattach tomorrow with the session intact — as long as it’s within your --time.

When you’re done, exit the shell to release the allocation (don’t sit on idle cores — it hurts your fair-share and blocks others).

17.1.1 Interactive apps in the portal

The web portal (Chapter 3) offers graphical interactive apps — a full XFCE desktop, RStudio, and almost certainly Jupyter — that launch as scheduled jobs behind the scenes. These are the friendliest way to do interactive/GPU notebook work without wrangling salloc and port-forwarding by hand.

17.2 GPU jobs

Request GPUs with --gres=gpu:<count> and target a GPU partition:

#!/bin/bash
#SBATCH --account=cowy-firesurro
#SBATCH --partition=mb-l40s          # or mb-h100, mb-a30, ...
#SBATCH --qos=normal
#SBATCH --gres=gpu:1                 # one GPU on the node
#SBATCH --cpus-per-task=8            # CPUs to feed the GPU
#SBATCH --mem=64G
#SBATCH --time=08:00:00

module purge
module load gcc/13.2.0 cuda-toolkit/12.6.1   # CUDA needs gcc 13.2, see below
nvidia-smi                                    # confirm the GPU is visible
python train.py

To request a specific GPU type you can also use the typed form, e.g. --gres=gpu:h100:2 for two H100s on one node.

17.2.1 Which GPU partition? Match it to the phase of work

GPU partition GPUs Typical wait Use for
mb-a30 8× A30 minutes development, proof-of-concept, debugging
mb-a6000 / mb-r6000 4× each short–moderate GPU dev, mid-size jobs
mb-l40s 8× L40S ~1 h+ inference, mid-size training
mb-h100 8× H100 seconds–hours large training / production only
Don’t develop on H100s

H100 nodes are the most contended resource on the machine — waits of several hours are normal when they’re busy (Chapter 13). Do your iterate-fast development on A30s, which you can usually get in minutes, and only submit to mb-h100 when you have a real training run that needs that horsepower. Check gpuavail and showpartitions before choosing.

The GPU compiler quirk

cuda-toolkit is built only against gcc/13.2.0, even though gcc/13.2.0 prints a deprecation warning nudging you to gcc/14.2.0. For GPU/CUDA work, load gcc/13.2.0 anyway and ignore the warning (Chapter 7). Inside containers, add --nv to expose the GPU (Chapter 8).

17.2.2 Checking GPU availability and usage

gpuavail                    # ARCC helper: free GPUs by type, right now
slurm_gpustat               # cluster-wide GPU utilization
sinfo -p mb-h100 -o "%P %t %G %D"   # H100 node states this second
nvidia-smi                  # inside a GPU job: is my code actually using the GPU?
nvtop                       # inside a GPU job: live GPU usage, like htop for GPUs

If nvidia-smi shows 0% utilization while your job runs, your code isn’t actually on the GPU — a common and expensive mistake. Verify early.

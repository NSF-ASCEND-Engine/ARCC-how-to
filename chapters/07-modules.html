7  Software modules

Software comes from Lmod modules you module load. The system is hierarchical: many packages are invisible until you load a compiler, so module avail only shows what’s reachable right now. Use module spider <name> to find a package and learn what to load first.

7.1 Why modules exist

A cluster has hundreds of users who need incompatible software: three versions of Python, five compilers, conflicting builds of GDAL. Modules let you load exactly the versions you want into your shell for this session, without affecting anyone else. Load a module and its programs appear on your PATH; unload it and they vanish.

module load gcc/14.2.0        # add gcc 14 to this shell
module list                   # what do I currently have loaded?
module unload gcc/14.2.0      # remove it
module purge                  # clear everything and start clean

7.2 The hierarchy

MedicineBow uses Lmod in hierarchical mode. Modules are arranged in layers:

  • Core modules are always visible: the compilers (gcc, nvhpc-sdk, oneapi), MPI, and standalone tools.
  • Compiler-dependent modules — Python, R, GDAL, NetCDF, HDF5, CUDA — are hidden until you load a compiler. They were built against a specific compiler, so Lmod won’t show them until you’ve picked one.

So a new user runs module avail, doesn’t see gdal, and concludes it isn’t installed. It is — just one layer down.

Use module spider, not module avail, to check whether something exists

module avail shows only what’s loadable given what you’ve already loaded. module spider searches the entire tree and tells you both that something exists and what to load first to reach it.

module spider gdal            # yes it exists; here are the versions
module spider gdal/3.13.0     # ...and exactly what to load before it

A typical geospatial stack, in order:

module purge
module load gcc/14.2.0        # 1. a compiler, first
module load gdal/3.13.0       # 2. now GDAL is reachable
module load netcdf-c/4.9.2-ompi

7.3 What’s installed (a tour)

Ask the machine for the current list with module spider, but roughly:

  • Compilers (core): gcc/{11.4.0, 11.5.0, 13.2.0, 14.2.0, 15.2.0}, nvhpc-sdk, oneapi, openmpi/5.0.10.
  • After loading a compiler: python/{3.10.6, 3.12.0, 3.14.4}, r/{4.4.0, 4.5.3}, gdal/{3.7.3, 3.13.0}, netcdf-c/4.9.2-ompi, hdf5/1.14.3*, cuda-toolkit/{12.4.1, 12.6.1}, openmpi/4.1.6, rclone/1.63.1.
  • Standalone: apptainer/{1.3.5, 1.4.1}, singularity/4.1.0, miniconda3/24.3.0, julia/{1.10.3, 1.11.6}.
CUDA needs the deprecated gcc/13.2.0

gcc/13.2.0 prints a deprecation warning pointing to gcc/14.2.0, but cuda-toolkit is only built against gcc/13.2.0. GPU users have to load it anyway:

module load gcc/13.2.0        # the one that warns you — CUDA needs it
module load cuda-toolkit/12.6.1

Ignore the warning here; it’s a packaging quirk.

7.4 Making a set of modules load automatically

Once you know the stack a project needs, save it as a named collection so you don’t retype it:

module purge
module load gcc/14.2.0 gdal/3.13.0 netcdf-c/4.9.2-ompi
module save geostack          # remember this set as "geostack"

# next session:
module restore geostack

Prefer module restore in submit scripts over hand-loading a long list — it’s reproducible and self-documents the environment your job needs.

Load modules in your submit script, not just interactively

Modules loaded on the login node don’t carry into a batch job. Put the module load / module restore lines inside your sbatch script so the job builds the same environment every time (Chapter 10).

When a package isn’t available as a module — or you need a pip/conda world — see the next chapter (Chapter 8).
